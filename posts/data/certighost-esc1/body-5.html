If a template is intended only for TLS server certificates, client authentication should be removed from its EKUs. Requester-controlled subjects and SANs should not be combined with authentication-capable purposes unless there is a documented requirement and additional approval controls. Manager approval or authorised signatures can provide a temporary guardrail but should not replace correct template design and access control.

Certificates issued through the affected template should be reviewed for unexpected privileged identities. Any unauthorised or assessment-issued certificates should be revoked, relevant certificate revocation data should be published, and compromised account passwords should be reset where credential material was recovered. Certificate revocation and password resets address different artefacts; changing a password alone does not remove an issued certificate's ability to authenticate while that certificate remains valid and accepted.

Certificate template creation and modification should be governed centrally. Organisations should maintain an inventory of enabled templates, their EKUs, subject-name behaviour, approval requirements and effective enrolment permissions. Automated checks should identify combinations associated with ESC1 and related AD CS attack paths before templates are published.

Domain controllers should enforce Microsoft's current strong certificate mapping protections, and CA audit logging should be enabled and forwarded for monitoring. Certificate requests containing privileged UPNs, unusual SIDs or unexpected templates should be investigated. Web Enrolment, RPC enrolment and other CA interfaces should only be exposed to the networks and systems that require them.

CertiGhost remediation should be handled independently by applying the relevant Microsoft security updates to affected CA hosts. Network controls that prevent arbitrary CA callbacks can reduce exploitability, but they should be treated as defence in depth rather than a substitute for patching.

Assessment Cleanup

Controlled computer accounts created during failed PoC attempts should be tracked and removed after testing. Certificate files, private keys, Kerberos caches and recovered hashes should be handled as sensitive credential material and deleted or transferred according to the engagement's evidence-handling requirements.

CA request records should normally remain available for audit correlation. Cleanup should remove attacker-controlled directory objects and local credential artefacts without erasing server-side evidence needed by the client to understand what occurred.

Conclusion

This assessment started with a current CVE check and ended with a conventional certificate template compromise. The CertiGhost PoC was valuable even though it did not complete: its failures exposed an incorrect CA endpoint, a cross-domain template ACL problem and a network path that permitted outbound access but blocked reverse callbacks.

The AD CS configuration contained a template intended for web certificates that granted broad enrolment, allowed the requester to choose the identity and supported client authentication. That combination allowed a low-privileged child-domain user to obtain a certificate for the forest-root Administrator, authenticate through PKINIT and confirm administrative command execution on the Certificate Authority.

AD CS assessment should account for forest structure, template semantics, effective permissions and network direction. Failure of a specific PoC did not exclude other certificate-based privilege escalation paths exposed by the same Certificate Authority.
