The default naming context represented the domain handled by the current DC. The Configuration naming context was forest-wide and contained the AD CS enrolment service objects and certificate templates. Tooling that constructed CN=Configuration,DC=child,DC=example from the supplied child-domain name queried an object that did not exist and returned noSuchObject.

The correct approach was to trust the naming contexts returned by RootDSE rather than deriving them from the authentication domain. The CA enrolment service could be located beneath the actual Configuration partition:

ldapsearch -LLL -x -H ldap://192.0.2.10 -D 'child.example\audit.user' -W -b 'CN=Enrollment Services,CN=Public Key Services,CN=Services,CN=Configuration,DC=corp,DC=example' '(objectClass=pKIEnrollmentService)' cn dNSHostName

The sanitised result separated two values that are often confused:

cn: CORP-CA
dNSHostName: CA01.corp.example

CORP-CA was the CA service name expected by certificate RPC requests. CA01.corp.example was the DNS hostname of the Windows server running the service. Supplying the hostname where the PoC expected the CA service name, or omitting the explicit CA IP, caused requests to be directed to the wrong endpoint.

Forest-Root Domain Controller Discovery

The forest-root DCs were then identified using DNS SRV records. Querying the child DC as the DNS server avoided relying on the assessment host's local resolver configuration:

for host in $(dig +short @192.0.2.10 _ldap._tcp.dc._msdcs.corp.example SRV | awk '{print $4}' | sed 's/\.$//'); do printf '%s -> ' "$host"; dig +short @192.0.2.10 "$host" A | paste -sd,; done

A generic SRV query can return multiple DCs in varying order. Selecting the first line with awk 'NR==1' therefore selected an inaccessible DC during the first attempt. The PDC-specific record provided a consistent target for the forest-root operations:

dig +short @192.0.2.10 _ldap._tcp.pdc._msdcs.corp.example SRV
0 100 389 ROOT-DC01.corp.example.

An Nmap check against the first generic result appeared to state that the host was online, but the command had used -Pn. In that mode, Nmap skips host discovery and assumes the target is up. The accompanying text Host is up, received user-set meant the user had instructed Nmap to proceed; it did not mean the host had replied. All tested ports returned no response.

This was a small but important lesson. DNS registration, host reachability and service reachability are separate questions, and tooling output should be read in the context of the options supplied.

Incorrect Certificate Authority Endpoint

The first PoC attempt supplied the CA service name but omitted the explicit CA IP. The script fell back to the supplied DC address and attempted certificate RPC against a domain controller that was not running the CA service.

DC: 192.0.2.10
CA service: CORP-CA
CA endpoint incorrectly selected: 192.0.2.10

The resulting error was:

ept_s_not_registered

This indicated that the expected RPC interface was not registered at the selected endpoint. It was not evidence that CertiGhost had been patched or that the template was safe. Supplying the correct CA service name and CA server IP resolved the endpoint error:

--ca CORP-CA
--ca-ip 192.0.2.30

Certificate Template Enrolment Permissions

The PoC defaulted to the Machine template. This template contained the required DNS name flags and permitted client authentication, making it technically suitable for the directory chase. The first controlled computer account had, however, been created in the child domain.

The template's enrolment permissions granted access to the forest-root Domain Computers group. A child-domain computer had a different domain SID and was not a member of that group. Authentication to the CA succeeded, but the certificate request was denied by policy:

0x80094012: Denied by Policy Module

This error was easy to misinterpret because the controlled computer was valid and could authenticate. The failure occurred later, when the CA evaluated the template ACL. Template suitability and effective enrolment rights must be assessed separately.

A controlled computer was then created in the forest-root domain. The first standalone Impacket attempt timed out because it tried to reach RPC endpoint mapper on TCP port 135, which was filtered from the assessment host. NetExec's add-computer module used the SMB \\samr named pipe directly and succeeded when TCP port 445 was available.

ROOT_MACHINE='AUDITPC01$'; ROOT_MACHINE_PASS='<REDACTED>'; nxc smb 192.0.2.20 -d child.example -u 'audit.user' -p "$USER_PASS" -M add-computer -o NAME="$ROOT_MACHINE" PASSWORD="$ROOT_MACHINE_PASS"

The new account belonged to the root-domain Domain Computers group and could use the Machine template. This removed the template ACL blocker but exposed the final CertiGhost dependency.

Certificate Authority Callback Connectivity

With the correct CA endpoint, root-domain computer account and suitable template, the request reached the callback stage. The CA returned:

0x800706ba: RPC_S_SERVER_UNAVAILABLE

The PoC debug output described this as a wrapper for a CA-side callback failure. The rogue services were listening successfully on 0.0.0.0:445 and 0.0.0.0:389, but no inbound connection appeared in their logs.

Packet capture confirmed that no callback traffic reached the assessment host:

sudo tcpdump -ni any -nn 'src host 192.0.2.30 and tcp and (dst port 389 or dst port 445)'

The first listener address was a VPN-assigned /32. It allowed the Kali system to initiate connections into the data centre, but unsolicited data-centre-to-client connections were not passed back through the VPN. The underlying office address was also tested because the office and data-centre networks were connected, but the CA could not reach the required ports there either.
